# CIP-0001: Localhost MCP control plane (bridle)

> CIPs describe HOW to achieve requirements (WHAT).  
> This CIP implements [REQ-0001](../requirements/req0001_localhost-privileged-mcp.md).

## Summary

Establish **bridle** (`lawrennd/bridle`) as a dedicated local MCP control
plane for Cursor agents. Privileged adapters (first: `gh`) run outside the
agent seatbelt sandbox; the agent talks only to localhost. DOAgent provides
the accountability layer for tool invocations. lynguine engages later as an
adapter to its existing server mode — not as the MCP host.

## Motivation

Cursor agent shells in this environment set `CURSOR_SANDBOX=seatbelt` and
force HTTPS through a local CONNECT proxy. Calls to `api.github.com` fail
with proxy **403**. `gh` then misreports the failure as an invalid keyring
token, even when the user's interactive terminal authenticates successfully
(`CURSOR_SANDBOX` unset, direct API HTTP 200).

Requesting Shell `required_permissions: ["all"|"full_network"]` did not lift
the seatbelt in affected threads. Copy-pasting `gh` commands into an
external terminal works but does not scale.

We need a **controlled** escape hatch: not “disable sandbox”, but a
user-owned localhost bridge with an allowlist and an audit trail.

Triggering incident: opening [lawrennd/mlai#1](https://github.com/lawrennd/mlai/pull/1)
(Deep GP pinball fix for [SheffieldML/GPy discussion #1001](https://github.com/SheffieldML/GPy/discussions/1001))
could not be completed from the agent shell.

## Detailed Description

### Architecture (layers)

```text
Cursor agent (sandboxed)
        │  MCP over localhost (NO_PROXY includes 127.0.0.1)
        ▼
lawrennd/bridle          ← this repo: policy, MCP tools, records
        │
        ├── adapters: gh, …     ← privileged CLIs in the user environment
        ├── DOAgent session     ← accountable tool invocations as shared records
        └── optional clients → lynguine server / other local services
```

| Layer | Role |
|-------|------|
| **MCP** | Cursor-facing protocol (what the sandboxed agent may call) |
| **bridle** | Control plane: allowlist, confirmations, adapter dispatch |
| **DOAgent** | Accountability fabric: record decisions, inputs, outcomes |
| **lynguine** | DOA *data* plane (interfaces, frames, server mode) — not the tool host |

### Decision: dedicated repo under `lawrennd`

**Yes.** Do not fold this into `lynguine`, `vibesafe`, or project repos
(GPy / PyDeepGP / mlai).

- **vibesafe** = project governance (CIPs, backlog, tenets)
- **lynguine** = DOA data management (+ existing localhost HTTP server)
- **bridle** = privileged agent I/O control plane

Name **bridle**: steer privileged actions without owning the horse. Prefer
over generic `harness` / `agent-tools` (junk-drawer risk).

### Decision: DOAgent (Cabrera) — yes for the middle

Use DOAgent so each tool call is a recorded action in a shared run (inputs,
policy decision, result/failure). That yields auditability: “the agent asked
to open a PR; bridle allowed it; here is the URL.”

Do **not** make DOAgent the MCP transport. Pattern:

1. Thin MCP tool handlers  
2. Policy gate (allowlist / optional confirm)  
3. DOAgent-shaped recording around adapter execution  

If the DOAgent dependency is heavy for v0, ship a compatible append-only
record schema first and swap in DOAgent sessions without changing the MCP
surface.

### Decision: lynguine MCP — adapter later, not in lynguine core yet

lynguine already solved a related problem with **server mode**
(`127.0.0.1:8765`, `ServerClient`). An MCP façade is natural, but:

1. **Short term:** bridle adapter `lynguine_*` → existing lynguine server  
2. **Medium term:** optional `lynguine-mcp` extra or thin package if stable  
3. **Longer DOA play:** bridle and lynguine as peers on shared interface data  

Putting MCP inside lynguine core now couples a Cursor-specific transport to
a general DOA library. Keep lynguine about data; bridle about privileged
agent I/O.

### Explicit non-goals (v0)

- Free-form `run_shell` / `gh "$@"` passthrough  
- Full DOAgent multi-agent topologies before one working `gh` adapter  
- Merging into VibeSafe  
- Requiring sandbox disable for routine PR workflows  

### First adapter: `gh`

Allowlisted tools (illustrative):

- `gh_pr_create`  
- `gh_pr_view` / `gh_pr_list`  
- Narrow `gh_api` (path allowlist only)

Credentials remain in the user's keyring; bridle runs in an **unsandboxed**
external process (terminal or LaunchAgent).

## Implementation Plan

1. **Repo bootstrap (this slice)**  
   - Create `~/lawrennd/bridle`, git init, install VibeSafe from
     `~/lawrennd/vibesafe`  
   - Document architecture in this CIP (Proposed)  
   - Capture REQ-0001  

2. **MCP skeleton**  
   - Python MCP server bound to localhost  
   - Cursor MCP config snippet in README  
   - Health/ping tool  

3. **`gh` adapter + policy**  
   - Allowlist + structured args (no shell string)  
   - Action log (DOAgent or compatible schema)  

4. **Hardening**  
   - Optional confirm for mutating ops  
   - Tests with mocked `gh`  
   - Document failure modes (bridle not running vs policy deny)  

5. **lynguine adapter (follow-on CIP)**  
   - Only after `gh` path is boring  

## Backward Compatibility

Greenfield repo. No existing API consumers.

## Testing Strategy

- Unit tests for policy allow/deny and argument validation  
- Integration test: with bridle running unsandboxed, sandboxed client
  (or curl to localhost MCP/HTTP façade) can complete a dry-run `gh`
  operation  
- Regression note: document the seatbelt + CONNECT 403 failure mode so
  future agents do not chase “invalid token” red herrings
