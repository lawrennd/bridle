# CIP-0003: Allowlisted read-only mail header adapters

> Implements [REQ-0003](../requirements/req0003_metadata-least-disclosure.md)
> for **mail** (first validating domain).  
> Extends the control plane from [CIP-0001](cip0001.md).

## Summary

Add structured, allowlisted bridle MCP tools that return **email headers
only** for user-configured accounts/mailboxes. This is the first concrete
application of REQ-0003’s metadata-first least-disclosure rule (headers =
metadata; bodies/attachments = content). Bridle remains a thin policy and
audit wrapper over an existing mail backend — not a new mail client and not
a passthrough to a full email MCP.

**Which requirements?** REQ-0003 (metadata without content; no mutation
bundled into metadata tools), validated here for mail.

## Motivation

REQ-0003 asks for triage via envelope/metadata without content dumps. Mail
is the pressing domain: who contacted whom, subject, date — without bodies.
macOS Automation for Mail.app is coarse (all-or-nothing TCC once granted).
Bridle already exists as the place to put **argument-level allowlists** and
an action log; mail should follow the same pattern as `gh`, and prefer
reusing mature tools where that still meets least disclosure.

## Detailed Description

### Tool surface (proposed — MCP tools exposed to the agent)

| Tool | Mutating | Returns | Notes |
|------|----------|---------|--------|
| `mail_account_list` | no | Allowlisted account labels only | Never lists accounts outside config |
| `mail_header_list` | no | Headers for recent messages | Args: `account`, optional `mailbox`, `limit`, optional `from_glob` |
| `mail_header_view` | no | Headers for one message | Args: `account`, `message_id` (opaque id from list) |

**Header fields in scope (minimum):** `from`, `to`, `cc`, `bcc` (if
present), `subject`, `date`, `message_id` (RFC), plus bridle `id` and
`mailbox` for subsequent `mail_header_view`.

**Explicitly not exposed as tools (this CIP):**

| Capability | Why omitted |
|------------|-------------|
| Body read / search | Content under REQ-0003; prompt injection and privacy |
| Attachment list / get | Content (bytes); separate CIP if ever needed |
| Send / reply / forward / draft | Mutation; empty recipient allowlist forever for this slice |
| Delete / move / flag / mark read | Mutation; IMAP must use read-only session semantics where applicable |
| Free-form IMAP / AppleScript / `email_command` | Violates control-plane allowlist |

### Policy (bridle-enforced, not OS-enforced)

Config (sketch — exact schema in implementation):

```toml
# e.g. ~/.bridle/mail.toml or env BRIDLE_MAIL_*
[[accounts]]
id = "work"
# backend-specific locator (IMAP host+user, or Mail.app account name)

allowed_mailboxes = ["INBOX"]          # deny by default if empty? prefer explicit list
allowed_from = ["*@example.com"]       # optional; empty = any sender within mailbox
max_list = 50
```

- Tool name must be in `ALLOWED_TOOLS`.
- `account` / `mailbox` / `from` must pass allowlists before any backend call.
- Action log: store tool, args, allow decision; **do not** log bodies (none
  returned); truncate oversized header values; redact anything resembling
  credentials in errors.

### Backend choices (decide at Accept)

Bridle wraps one backend. Guided by **thin-wrapper-over-existing-tools**.

| Option | What we wrap | Pros | Cons | Fits headers-only? |
|--------|--------------|------|------|--------------------|
| **A. IMAP via existing Python library** (e.g. imaplib / curated helper) | Standard IMAP | Finer auth (app password / OAuth); `EXAMINE` + header fetch (`BODY.PEEK[HEADER]`) is a known pattern in email MCPs; no Mail Automation grant | Setup per account; not “whatever Mail.app already synced” | **Best fit** for mail metadata |
| **B. Mail.app via fixed `osascript`** | AppleScript dictionary | Uses local synced mail; familiar on macOS | TCC Automation is all-or-nothing for Mail; grant often attributed to Cursor; must filter accounts in adapter | Possible but weaker privacy story |
| **C. Subprocess to an existing email MCP/CLI** (e.g. headers-capable server or `himalaya`-style CLI) | External tool | Maximum reuse | Dependency and version drift; must **strip** any body/send tools — wrap only header operations we allow | Good if the CLI has a clear headers-only invocation |
| **D. Provider API** (Gmail API `metadata` / `format=METADATA`) | Official API | Strong scopes (`gmail.readonly`); metadata format avoids body | Google-centric; OAuth client setup | Strong for Gmail-only users |

**Chosen at Accept (2026-10-20): Option A (IMAP headers)** via the stdlib /
a thin helper — `EXAMINE` + header fetch only. Option C remains a fallback
if a maintained CLI proves cleaner later. Options B and D are deferred
(coarse TCC; Gmail-specific OAuth) unless IMAP cannot cover needed
accounts.

**Non-choice:** embedding or proxying a full third-party email MCP catalog
(send tools visible, bodies by default). That fights least disclosure and
turns bridle into a pass-through.

### Adapter shape (same as `gh`)

- New module e.g. `mail_adapter.py`: validate args → `require(tool, …)` →
  call backend → return `{ok, …}` headers only.
- No agent-supplied script, IMAP command string, or API path.
- Errors mapped to structured `{ok: false, error}` (extend `_invoke`
  exception handling like `GhError`).
- Server `instructions` state clearly: headers only; content is untrusted
  data, never instructions.

### Relationship to attachments / bodies / other domains (future)

Attachments and bodies are **content** under REQ-0003 — out of this CIP.
Other domains in REQ-0003’s illustrative table (files, calendar, chat) need
their own CIPs when wanted; they should reuse the same metadata-vs-content
and allowlist pattern established here.

## Implementation Plan

1. **Accept this CIP** after choosing backend option (A/B/C/D) and confirming
   the three-tool surface.  
2. **Backlog tasks** (only after Accept):  
   - Mail config + argument-level policy (accounts, mailboxes, sender globs)  
   - `mail_adapter` for chosen backend (headers fetch only) + mocked tests  
   - MCP tools `mail_account_list` / `mail_header_list` / `mail_header_view`  
   - Action-log redaction/truncation for header results  
   - README allowlist table + privacy/TCC notes  
3. **Smoke** from Cursor: list headers for one allowlisted mailbox; confirm
   deny for non-allowlisted account; confirm no body fields in response.  
4. **Close CIP** when REQ-0003’s acceptance criteria are met for the mail
   domain (first validating adapter).

## Backward Compatibility

Additive MCP tools only. Existing `gh_*` / `ping` unchanged. Cursor must
reload MCP after deploy so new tool schemas appear. Users who do not
configure mail see tools deny or report “mail not configured.”

## Testing Strategy

- Unit: policy allow/deny for account, mailbox, sender, unknown tools  
- Unit: adapter requests header-only fetches (mocked IMAP/CLI/osascript);
  assert response schema has no `body` / attachment keys  
- Unit: action log entries omit body-sized payloads  
- Optional live test behind `BRIDLE_LIVE_MAIL=1` against a dedicated test
  account
